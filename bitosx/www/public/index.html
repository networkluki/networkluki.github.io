BitosX

An advanced password manager built around zero-knowledge encryption and a strict separation between account authentication and vault encryption.

Encrypted locally • Fail closed • No backdoors

Desktop app (GitHub releases) Web account

What BitosX is

Vault data is encrypted on your device before it ever reaches a server. The backend never needs your master password, your raw encryption keys, or a single decrypted password.

Zero-knowledge by design

The master password, the vault key and the decrypted contents never leave the device. A compromised server must not be able to reveal vault plaintext. This rule is enforced at the API contract and database schema level, not just promised.

Two separate systems

Your account password signs you in to the service. Your master password decrypts your vault. They are different secrets, hashed and derived in different places, and are never conflated in code, storage or transport.

Fails closed

Unknown formats, tampered files, wrong passwords and unexpected errors all end the same way: nothing is decrypted, nothing falls back to plaintext, and an unlocked vault locks itself. There is no recovery key and no universal decryption key.

How your vault is protected

Vetted primitives only, composed the boring way: Argon2id derives a key from the master password, and that key only ever wraps a random vault key.

master password
      │  Argon2id(salt, 256 MiB, 3 passes, 4 lanes)
      ▼
key-encryption key (256-bit)
      │  AES-256-GCM wrap   (AAD = vault header)
      ▼
random vault key (256-bit, CSPRNG)
      │  AES-256-GCM encrypt (fresh nonce each write)
      ▼
encrypted vault — the only thing written to disk
PropertyValue
Key derivationArgon2id, 256 MiB memory, 3 iterations, parallelism 4, 32-byte key
EncryptionAES-256-GCM, 128-bit tag, 96-bit random nonce per operation
Salt128-bit, random per vault
Tamper detectionHeader fields bound as associated data; any change fails authentication
Untrusted inputVault file capped at 16 MiB; KDF parameters bounded before any derivation
Wrong password vs tamperingIndistinguishable: one generic error

Full details, including an explicit list of what BitosX does not protect against, live in the repository: SECURITY_MODEL.md, THREAT_MODEL.md, CRYPTOGRAPHY.md.

What works today

Honest status, no marketing. The desktop application (0.7.0) is a complete local encrypted vault. Server features are being built behind it, one audited layer at a time.

Desktop app — available

  • Create, unlock and lock a local vault protected by a master password
  • Add, edit, delete, favourite and search login items
  • Automatic locking on inactivity, workstation lock and suspend
  • Change the master password, rotate the vault key, strengthen key derivation
  • Encrypted backup and authenticated restore
  • Clipboard copy with timed clear and “do not keep” markers
  • Cryptographically secure password generator and a local Security Center
  • Windows, Linux and macOS builds (tested on all three; run on Windows)

Online account — phase 1

  • Email-first registration: no password is accepted until you own the address
  • Email verification sets the account password (12–128 characters)
  • Sign in, short-lived access tokens, rotating refresh tokens
  • See and revoke your own sessions at vault.bitosx.se

Not yet

  • Vault synchronisation between the desktop app and the server
  • Reading your vault in the browser
  • Browser extension, mobile apps, password reset, two-factor authentication

Service status

Three hostnames, three jobs. The API status below is fetched live from your browser; if the API is not reachable from here, that is shown as such rather than guessed.

  • bitosx.se static This page. Product information only. No account data, no cookies, no tracking.
  • vault.bitosx.se phase 1 Web account: register, verify your email, sign in, manage sessions. Talks to the API directly from your browser.
  • api.bitosx.se checking… Account and session API, operated alongside the desktop app. Behind Cloudflare and a reverse proxy; the service itself only listens on loopback.

Roadmap

  1. Phase 1now

    Public site and web account. This page, plus registration, email verification, sign-in and session management against the existing account API. No vault data is involved anywhere online.

  2. Phase 2next

    Desktop app signs in. The desktop app gets a real API client: account sign-in, session handling and token refresh, still with no vault data leaving the device.

  3. Phase 3planned

    Encrypted sync. The server stores the encrypted vault envelope as opaque bytes. The desktop app uploads and downloads ciphertext only; conflicts fail closed rather than merge blindly.

  4. Phase 4planned

    Web vault. Decrypting in the browser with the master password, using the same Argon2id and AES-256-GCM parameters as the desktop app, so the server stays zero-knowledge even when you read your vault online.
